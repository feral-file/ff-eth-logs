# BigQuery cost probe, 2026-08

Record of the probe that sized the warehouse and produced the `v1` export (ff-indexer-v2 issue #130, Phase 2). Run on **2026-08-28** by one BigQuery script, `warehouse_extract.sql` (section 9), in project `indexer-eth-logs`, bucket `gs://eth-logs`.

## 1. Question

Whether the immutable half of the indexer's Ethereum RPC traffic — every historical `eth_getLogs` — can be self-hosted in PostgreSQL at a size one instance can carry, and what a full export costs. Go/no-go before any schema landed.

## 2. Dataset

`bigquery-public-data.crypto_ethereum` (community dataset; `logs`: `log_index, transaction_hash, transaction_index, address, data, topics ARRAY<STRING>, block_timestamp, block_number, block_hash`, partitioned by `DATE(block_timestamp)`), chosen over `goog_blockchain_ethereum_mainnet_us` for freshness. Measured 2026-08-28 from `INFORMATION_SCHEMA.PARTITIONS` (metadata only, free):

| Table | Rows | Logical size | Newest partition |
| --- | --- | --- | --- |
| `blocks` | 25,842,830 | 0.039 TB | 20260826 |
| `logs` | 7,375,431,666 | 3.93 TB | 20260826 |

Dataset head: block **25,842,829** at 2026-08-26 23:59:59 UTC — daily partitions, about two days behind mainnet, so the RPC catch-up after a load is the age of the export at start (~14k blocks at export time).

## 3. Shape rules (the extract `WHERE` clause)

The materialised set is the intersection of "a signature the indexer subscribes to" and "the shape the indexer's parsers accept", mirroring `internal/eventset.Keep` — the two must stay in lock-step:

| Event | Rule |
| --- | --- |
| `Transfer(address,address,uint256)` | exactly 4 topics (3 topics is ERC-20, 1 topic is CryptoKitties; both skipped by the indexer since ff-indexer-v2 60eba9b) |
| `TransferSingle`, `TransferBatch` | 4 topics |
| `MetadataUpdate`, `BatchMetadataUpdate` | 1 topic |
| `URI` | 2 topics |
| `PunkTransfer`, `Assign`, `PunkBought` | address = `0xb47e3cd837ddf8e4c57f05d70ab865de6e193bbb` only |

Hex strings are converted to `BYTES` in the extract so Parquet → `bytea` needs no decoding; `data` NULL becomes empty bytes.

## 4. Rehearsal (one day: 2026-08-20, blocks 25,792,602–25,799,779)

Run first against a single day (export prefix `gs://eth-logs/eth-log-warehouse/v0-rehearsal`) to catch script errors before the paid scan:

- Bugs found for free: `rows` is a reserved alias; `OFFSET(0)` overflows on zero-topic (anonymous) logs because BigQuery evaluates every predicate branch — `SAFE_OFFSET` in a subquery; `hash` / `timestamp` are reserved words in the blocks export.
- Kept **72,430 logs / 7,178 blocks** ≈ 10 per block ≈ 2.2 M per month. Densest block: 3,085 kept logs.
- `data`: 399 KB total — ERC-721 `Transfer` 0 B; `TransferSingle` 64 B; `TransferBatch` avg 257 B, max 1,152 B; `URI` avg 135 B. The 500 B/row model holds.
- Parquet: 72,430 rows → 2.5 MB ≈ **34 B/row** on GCS. Empty partitions produce a 1.4 KB zero-row file (the loader tolerates it). Blocks export: 4,048 files, 1.16 GiB, 25,842,830 rows, every number 0 … 25,842,829 present.
- External-table round-trip: 72,430 rows, 72,430 distinct `(block_number, log_index)`; all hash columns land as `BYTES`.

## 6. Verification

- **RPC diff** — blocks 25,792,602–603 fetched from the dev RPC with the ingestion filter (topic0-only, no addresses) returned **1,463 logs**; the shape rules keep **17**; those 17 are tuple-for-tuple identical to the extract (block, log index, tx hash, address, topics 0–3, data). The other 1,446 are 3-topic ERC-20 `Transfer`s — the indexer downloads ~730 logs per block to keep ~8.
- **Parquet round-trip** — an external table over the exported files reproduced the materialised table's row count and distinct `(block_number, log_index)` count, and every hash column read back as `BYTES`.
- **BigQuery logical size** for the same rows: 98 GB, so the PostgreSQL model's 2× is index overhead, as expected.

## 7. Gate decision

Decision table from the plan and the outcome:

| Outcome | Call |
| --- | --- |
| kept rows ≤ ~600 M and data tail small (≤ ~300 GB modelled) | **Postgres as designed** ← 402 M rows, 205 GB |
| 600 M – 1.2 B (300–600 GB) | Postgres with the cheap levers applied up front |
| > 1.2 B or `data` tail dominates | ClickHouse single node |

**Postgres as designed.** 205 GB on one instance, no levers needed up front; ClickHouse is off the table. Storage at block-storage rates ≈ $0.10/GB/month → ~$25/month for a 250 GB volume with two years of headroom (managed PostgreSQL storage is pricier — quote both when choosing hosting).

## 8. Export layout and Parquet schema

```text
gs://eth-logs/eth-log-warehouse/v1/
  logs/part=000/logs-*.parquet      blocks 0 … 999,999          (part = block_number / 1,000,000,
  logs/part=001/logs-*.parquet                                    the same boundaries as eth_logs_pNNN)
  …
  logs/part=025/logs-*.parquet      blocks 25,000,000 … 25,842,829
  blocks/blocks-*.parquet           every block 0 … 25,842,829
```

Files are unsorted within a partition (~256k rows per file; the export carries no `ORDER BY` because BigQuery would funnel each partition through one worker) — the loader sorts each directory in PostgreSQL before inserting. Read with `parquet-go` v0.32.0.

**logs** (`internal/backfill.logRow`):

| Column | Parquet type | Postgres |
| --- | --- | --- |
| `block_number` | optional int64 | `eth_logs.block_number` |
| `log_index` | optional int64 | `log_index` (int32) |
| `tx_index` | optional int64 | `tx_index` (int32) |
| `tx_hash` | binary | `tx_hash` |
| `address` | binary | `address` |
| `topic0` … `topic3` | binary, NULL when absent | `topic0` … `topic3` (NULL passed through) |
| `data` | binary | `data` (NULL → empty) |
| `block_timestamp` | int64 TIMESTAMP(MICROS) | ignored — `eth_blocks.ts` carries it |

**blocks** (`blockRow`):

| Column | Parquet type | Postgres |
| --- | --- | --- |
| `number` | int64 | `eth_blocks.number` |
| `block_hash` | binary | `hash` |
| `ts` | int64 (unix seconds) | `ts` |

## 9. `warehouse_extract.sql`

Re-runnable as one script in the console or with `bq query --use_legacy_sql=false < warehouse_extract.sql`. Set "Maximum bytes billed" to 4 TB first; change `bucket` to a new version prefix rather than overwriting `v1`.

```sql
-- Ethereum log warehouse: single-pass extract (issue #130, Phase 2).
-- Runs as ONE BigQuery script (console or `bq query --use_legacy_sql=false < warehouse_extract.sql`).
--
-- 1. Materialize the warehouse set from the 7.4 B-row public logs table (the only scan
--    of the big table: ~3.4 TB billed, ~$21 list, ~$15 after the monthly free TiB).
-- 2. Export it to GCS as Parquet, one directory per 1,000,000 blocks — the same
--    partition boundaries the Postgres `eth_logs` table uses.
-- 3. Export blocks (number, hash, unix timestamp) for the `eth_blocks` table.
-- 4. Compute every sizing number from the small extract table (cents).
--
-- Project indexer-eth-logs, bucket gs://eth-logs (must be in the US multi-region). Before running,
-- set "Maximum bytes billed" to 4 TB in the console query settings as a hard stop.

DECLARE punks  STRING DEFAULT '0xb47e3cd837ddf8e4c57f05d70ab865de6e193bbb';
DECLARE bucket STRING DEFAULT 'gs://eth-logs/eth-log-warehouse/v1';
DECLARE sig_transfer STRING DEFAULT '0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef';
DECLARE sig_1155_single STRING DEFAULT '0xc3d58168c5ae7397731d063d5bbf3d657854427343f4c083240f7aacaa2d0f62';
DECLARE sig_1155_batch STRING DEFAULT '0x4a39dc06d4c0dbc64b70af90fd698a233a518aa5d07e595d983b8c0526c8f7fb';
DECLARE sig_4906_update STRING DEFAULT '0xf8e1a15aba9398e019f0b49df1a4fde98ee17ae345cb5f6b5e2c27f5033e8ce7';
DECLARE sig_4906_batch STRING DEFAULT '0x6bd5c950a8d8df17f772f5af37cb3655737899cbf903264b9795592da439661c';
DECLARE sig_1155_uri STRING DEFAULT '0x6bb7ff708619ba0610cba295a58592e0451dee2622938c8755667688daf3529b';
DECLARE sig_punk_transfer STRING DEFAULT '0x05af636b70da6819000c49f85b21fa82081c632069bb626f30932034099107d8';
DECLARE sig_punk_assign STRING DEFAULT '0x8a0e37b73a0d9c82e205d4d1a3ff3d0b57ce5f4d7bccf6bac03336dc101cb7ba';
DECLARE sig_punk_bought STRING DEFAULT '0x58e5d5a525e3b40bc15abaa38b5882678db1ee68befd2f60bafe3a7fd06db9e3';
DECLARE part INT64 DEFAULT 0;
DECLARE max_part INT64;

CREATE SCHEMA IF NOT EXISTS `indexer-eth-logs.eth_warehouse` OPTIONS (location = 'US');

-- 1. Materialize. Shape rules mirror what the indexer's parsers accept (see plan §1):
--    Transfer must carry 4 topics (3-topic = ERC-20), 1155 transfers 4, MetadataUpdate /
--    BatchMetadataUpdate 1, URI 2, CryptoPunks events only from the CryptoPunks contract.
--    Hex strings become BYTES here so Parquet -> Postgres bytea needs no decoding.
CREATE OR REPLACE TABLE `indexer-eth-logs.eth_warehouse.logs`
PARTITION BY RANGE_BUCKET(block_number, GENERATE_ARRAY(0, 40000000, 1000000))
CLUSTER BY block_number
AS
SELECT
  block_number,
  log_index,
  tx_index,
  FROM_HEX(SUBSTR(transaction_hash, 3))               AS tx_hash,
  FROM_HEX(SUBSTR(address, 3))                        AS address,
  FROM_HEX(SUBSTR(t0, 3))                             AS topic0,
  FROM_HEX(SUBSTR(t1, 3))                             AS topic1,   -- NULL when absent
  FROM_HEX(SUBSTR(t2, 3))                             AS topic2,
  FROM_HEX(SUBSTR(t3, 3))                             AS topic3,
  FROM_HEX(SUBSTR(IFNULL(data, '0x'), 3))             AS data,     -- empty bytes for ERC-721
  block_timestamp
FROM (
  -- SAFE_OFFSET everywhere: anonymous events have zero topics, and BigQuery evaluates
  -- every predicate branch, so a plain OFFSET(0) overflows on them.
  SELECT block_number, log_index, transaction_index AS tx_index, transaction_hash, address, data, block_timestamp,
         topics[SAFE_OFFSET(0)] AS t0, topics[SAFE_OFFSET(1)] AS t1,
         topics[SAFE_OFFSET(2)] AS t2, topics[SAFE_OFFSET(3)] AS t3,
         ARRAY_LENGTH(topics) AS n
  FROM `bigquery-public-data.crypto_ethereum.logs`
)
WHERE (t0 = sig_transfer                                 AND n = 4)
   OR (t0 IN (sig_1155_single, sig_1155_batch)           AND n = 4)
   OR (t0 IN (sig_4906_update, sig_4906_batch)           AND n = 1)
   OR (t0 = sig_1155_uri                                 AND n = 2)
   OR (t0 IN (sig_punk_transfer, sig_punk_assign, sig_punk_bought) AND address = punks);

-- 2. Export logs, one directory per 1M blocks (partition pruning makes each iteration cheap).
--    No ORDER BY: BigQuery would funnel each partition through one worker; the loader
--    sorts a directory by (block_number, log_index) before COPY instead.
SET max_part = (SELECT DIV(MAX(block_number), 1000000) FROM `indexer-eth-logs.eth_warehouse.logs`);
WHILE part <= max_part DO
  EXECUTE IMMEDIATE FORMAT("""
    EXPORT DATA OPTIONS (
      uri = '%s/logs/part=%03d/logs-*.parquet',
      format = 'PARQUET', compression = 'SNAPPY', overwrite = true)
    AS SELECT * FROM `indexer-eth-logs.eth_warehouse.logs`
       WHERE block_number BETWEEN %d AND %d
  """, bucket, part, part * 1000000, part * 1000000 + 999999);
  SET part = part + 1;
END WHILE;

-- 3. Blocks: number, hash, unix timestamp (scans ~3 GB).
EXECUTE IMMEDIATE FORMAT("""
  EXPORT DATA OPTIONS (
    uri = '%s/blocks/blocks-*.parquet',
    format = 'PARQUET', compression = 'SNAPPY', overwrite = true)
  AS SELECT number, FROM_HEX(SUBSTR(`hash`, 3)) AS block_hash, UNIX_SECONDS(`timestamp`) AS ts  -- hash/timestamp are reserved words
     FROM `bigquery-public-data.crypto_ethereum.blocks`
""", bucket);

-- 4. Sizing numbers, all from the extract (Q1 + Q2 + Q3 of the plan in one go).
CREATE OR REPLACE TABLE `indexer-eth-logs.eth_warehouse.stats_by_year_event` AS
SELECT
  EXTRACT(YEAR FROM block_timestamp) AS yr,
  CONCAT('0x', TO_HEX(topic0))       AS topic0,
  COUNT(*)                           AS logs,
  SUM(LENGTH(data))                  AS data_bytes,
  AVG(LENGTH(data))                  AS avg_data_bytes,
  MAX(LENGTH(data))                  AS max_data_bytes
FROM `indexer-eth-logs.eth_warehouse.logs`
GROUP BY yr, topic0;

CREATE OR REPLACE TABLE `indexer-eth-logs.eth_warehouse.stats_totals` AS
SELECT
  COUNT(*)                           AS logs,
  SUM(LENGTH(data))                  AS data_bytes,
  COUNT(DISTINCT address)            AS contracts,
  COUNT(DISTINCT topic1)             AS distinct_topic1,
  COUNT(DISTINCT topic2)             AS distinct_topic2,
  COUNT(DISTINCT topic3)             AS distinct_topic3,
  MIN(block_number)                  AS first_block,
  MAX(block_number)                  AS last_block,
  (SELECT MAX(c) FROM (SELECT COUNT(*) AS c FROM `indexer-eth-logs.eth_warehouse.logs` GROUP BY block_number)) AS densest_block_logs,
  (SELECT COUNT(*) FROM `indexer-eth-logs.eth_warehouse.logs`
     WHERE block_timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)) AS logs_last_30d
FROM `indexer-eth-logs.eth_warehouse.logs`;

SELECT * FROM `indexer-eth-logs.eth_warehouse.stats_totals`;
```

The materialised BigQuery table can be deleted once the stats are recorded (~$0.02/GB/month otherwise); the GCS export stays as the DR source (~$0.02/GB/month, ≈ 16 GB).
